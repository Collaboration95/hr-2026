Deep dive

Five changes account for most of the speed-up.

Plotline's decision layer re-checks a registered plot 44× faster than the first version, and a new boundary 5.2× faster. A few changes produced those numbers; they are described here in the order they were made.

In brief
  • Five changes: keep only what the decision reads; find a registered plot's cells once; decode on the packed bit-planes; scan small polygons in plain Python; drop NumPy for re-checks. A leaner shared reducer helped all of them.
  • Two separate scoreboards. Registered plots: 24× at the start, 44× now (83× without NumPy). New boundaries: 2.2× at the start, 5.2× now. All measured hot, against the retained original path (P0). The two are never combined into one multiple.
  • No phase changed an answer, a stored byte or a file format. The same proof, 744,732 of 744,732 cells, was re-run after every phase.
1 · Measurement basis

Each multiple depends on its baseline and its clock

Every multiple here is measured against the original query path from version 1, retained as the baseline and called P0. It reads three Hansen bands and builds a 101-bin canopy histogram. P0 is re-measured in every benchmark run, so a multiple can drift about half a percent without any code change.

Each multiple also belongs to one of three clocks, and multiples from different clocks are not comparable.

Hot

The layer is already loaded and the code has warmed up. One pass over the 17 supplied plots is timed and repeated hundreds of times. This is the per-plot cost once the layer is local.

Fresh process

A new Python process loads the layer and answers the 17 plots. Imports are done first; start-up is not counted. A smaller layer shows up here.

End-to-end

Python is launched from scratch and prints the answer. The time includes interpreter start-up (about 14.6 ms) and importing NumPy (about 25 ms). A do-nothing child in the harness already costs 20.1 ms.

Path codes

Each path is a different way of answering the same question. The suffix d means the decision level (s is the slightly larger screening level).

Breakthrough 1 · decision layers

Keep only what the decision reads.

The EUDR screen asks whether a cell was forest on 31 December 2020 and whether that forest has been lost since. Nothing in that question reads the 2000 canopy percentage, which is 72% of Hansen's bytes, or the loss years before the cut-off. The original query still loaded three Hansen bands and built a 101-bin canopy histogram on every call.

The decision layer drops all of that and keeps one small band: a 20-value code per cell. The original layers are 623,237 B; the decision store is 6,146 B, 99.0% smaller.

CaveatHot, this step is worth only 1.6×, because both paths still pay to find the cells inside a polygon. A plain GeoTIFF of the same decision codes is already 98.6% smaller, so the gain comes from the layer analysis, not from a codec. The structure-aware encoding adds the last 28%.
Go deeper: what the 20 codes are technical

Each Hansen cell becomes one of 20 codes: unknown, water, or land crossed with three forest states (not forest, forest, forest unknown in 2020) and six loss states (none, 2021 to 2025). The decision level additionally forgets the loss year on land that was not forest in 2020. The code space and the one reducer that turns a 20-bin histogram into the contract answer live in engine/decision_summary.py.

Breakthrough 2 · registered-plot index and answer table

Find a registered plot's cells once, then reuse them.

EUDR plots are registered once and re-checked every time a layer updates. Which cells sit inside a plot depends on the plot's boundary and the grid, not on the layer's values. So the expensive part, finding the cells, can be done once and saved as a short list of cell numbers. A re-check then counts the codes at those cells and turns the count into the answer.

That took the re-check from 85.4 µs per plot to 3.55 µs at the start (24×), and to 1.90 µs now (44×). The index gave the initial gain; a leaner reducer (breakthrough 5) improved it further.

SummaryEach registered plot's cells are found once, which makes re-checks 44× faster; the answer table, around 410×, is a cache.
Why the 410× is a cacheThe answer table is a materialised view: each registered plot's full answer, stored under a key of plot ID, geometry hash and layer (store) hash. A changed boundary or layer misses the key, so a stale answer is never returned. It only answers plots registered in advance. New boundaries do not get it; they get the P4 path at about 5×.
Go deeper: how the index and table work, and what hashing costs technical

build_registry in engine/decision_index.py stores each plot's in-chip flat cell indices (row × width + column, int32, sorted). registry_evaluate is a bincount of the codes at those indices, passed to the shared reducer. table_lookup returns the stored output only on an exact plot, geometry, layer and level match, otherwise nothing.

The realistic workflow stores each plot's geometry hash at registration. If a service instead re-hashes the polygon on every call, cost rises: P5d 1.90 to 5.97 µs, P6d 0.21 to 3.65 µs per plot. The 44× and 410× figures use the precomputed key.

Breakthrough 3 · Phase 1

Decode on the packed bit-planes.

The decision store keeps the map as a few yes/no planes (is it unknown? water? forest?) packed eight cells to a byte, plus a short list of loss-year events. The first reader unpacked every plane into 744,732 separate cells before it checked or used any of them.

Phase 1 does its checks on the packed bytes (93 KB), places the sparse loss years only where an event is, and finds ranked event cells by counting set bits. The file bytes and format did not change. Reading the decision store went from 2.5 ms to 0.67 ms (3.8×).

Go deeper: the three Phase 1 changes technical

_decode_split and read_store in engine/decision_store.py: the plane checks run on strip-order packed bytes and only the dense forest plane is expanded. A side effect: the validator's crafted-blob memory case now peaks near 6 MB instead of about 50 MB. The other two changes: the histogram reduction in summarize_counts (1.6 to 2.2× on its own) and polygon selection in fast_select_cells, which now builds the polygon straight from one coordinate array and paints ambiguous-cell rectangles without np.add.at. It calls a few shapely.lib functions directly, so it depends on the pinned shapely 2.1.2.

Breakthrough 4 · Phase 2 (tuned in Phase 4)

For a small polygon, a plain Python loop beats NumPy.

For a new boundary there is no saved list of cells, so they must be found. The rule is the centre rule: a cell counts if its centre is inside the plot. A scanline does it: for each map row, find where the boundary crosses the row; the centres between crossings are inside.

A plot is only about 120 cells. NumPy pays a fixed cost on every call, and at that size the cost exceeds the work. Phase 2 therefore scans small windows in plain Python and builds the histogram straight from the runs of selected centres. Ambiguous centres, such as an edge exactly through a centre, still go to exact GEOS geometry tests, so the result stays exact.

New boundaries went 3.0× to 5.0× in Phase 2 (2.2× at the start, 5.2× now).

Go deeper: when the Python scan is used, and the Phase 4 tuning technical

In engine/decision_index.py: windows up to 500 rows × edges (and 4,096 cells) always use the Python scan. Phase 4 also lets it take 500 to 2,000, unless the boundary changes rows more than 150 times in total (a "sawtooth"), where the NumPy scan is faster. The reason: a 224-shape sweep found the Python scan costs about 0.17 µs per row an edge crosses, and rows × edges predicts its time poorly (R² of 0.66, against 0.99 for a fit on edges and row crossings). The two scans were already proven identical. On the 17 plots every polygon was already under the first threshold, so the Phase 4 rule change did not touch them.

Breakthrough 5 · Phases 2 to 4

Drop NumPy for re-checks, and make the shared reducer lean.

This is the only change that moves the whole-process time. A fresh Python process spends about 25 ms just importing NumPy. A registered re-check only needs the codes at a few hundred cells, so it never needed NumPy.

The NumPy-free re-check (engine/decision_lite.py) reads and validates the store using only the standard library, then decodes codes only at the registered cells, straight from the packed planes. It never builds the 744,732-cell raster. End-to-end time for a registered re-check halves, 50.0 to 24.9 ms, and peak memory drops from 37 to 23 MB.

A reducer twice as lean

Every live answer ends in one function, the reducer, that turns the 20-bin histogram into the contract answer. In Phase 3 it unpacks the 20 numbers by name instead of slicing, zipping and calling a nested helper: about 1.6 to 0.8 µs per call. That alone lifted the registered index from 33× to 44× and the NumPy-free re-check from 44× to 65×. In Phase 4 a trusted-integer entry skips a list conversion that callers who already hold ints do not need: the NumPy-free re-check goes from 65× to 83× (1.31 to 1.02 µs per plot).

Without that pin, the NumPy index path is the one that checks the decoded raster.
4 · What is left

No single stage dominates a new-boundary check

A new boundary now costs about 16 µs. An independent audit of the 17 plots measured each stage. The largest, scanning the rows, is 30% of the total. Every other stage is smaller, so no single remaining change would double the speed.

6 · Alternatives considered

No better option was found for small exact plots on a CPU

Phase 4 included a review of papers, forums and engineering options. The centre rule is the standard zonal-statistics default (GDAL, rasterstats). The closest research, Raster Join, does what Plotline does in its exact form (a fast interior pass and exact checks at the border); its bounded form gives up exactness, which this use case cannot accept. Other approaches do not fit plots of about 120 cells.

9 · Design limits

Design limits

  • Edge cells are all-or-nothing. Under the centre rule a cell counts for a plot when its centre lies inside the boundary; cells are about 0.076 ha. Partial edge coverage and the 0.5 ha minimum area are not modelled.
  • JRC is sampled once per Hansen cell, at the centre of its 3 × 3 block. The alternatives (majority, any forest) give the same decision for all 17 plots, but only one plot has mapped forest.
  • The layer is rule-specific. A changed rule or an added layer means re-deriving from the lossless audit tier: seconds per region, about 7 CPU-minutes per tile (estimated).
  • The largest speed-ups need registered plots. The 44× to 410× figures apply to plots registered in advance; a new boundary gets 5.2×.
  • Storage was measured on a whole tile and query timing on one region.
10 · Short version

The speed story in one paragraph

A short account of how the speed was reached.

SummaryPlotline gets its speed by deleting work, not by tuning. It keeps only what the decision reads, so there is almost nothing to load. It finds each registered plot's cells once, which makes re-checks 44× faster for registered plots. It no longer unpacks the map into 744,732 cells. For new boundaries it scans small polygons in plain Python, about 5× faster. For re-checks it drops NumPy, which halves the whole run. No change altered an answer: all 744,732 cells still match.
