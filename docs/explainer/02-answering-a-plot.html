01 / Which pixels belong?

Keep a cell if its centre is covered.

Imagine pegs at the centres of graph-paper squares. Stretch a farm’s boundary around them. The centre rule keeps a whole cell when its centre lies inside the polygon or exactly on its boundary. Merely touching a corner of the cell’s square is not enough.

Precisely, select_cells() creates candidate centres on the original, unbounded grid, then calls covers(polygon, points) in Shapely, Python’s geometry library. Covers is boundary-inclusive: a point exactly on an exterior edge, vertex or hole boundary counts. A point strictly inside a hole does not.

Use the selector with arrow keys; use the slider’s arrow keys to move the outline. The white / dark solid rectangle is the available chip. The grid continues beyond it. This widget illustrates the rule in browser JavaScript; the engine’s Shapely predicate is the authoritative implementation.

Holes and separate parts.

A hole removes its interior, but its boundary still belongs to the polygon under covers. A MultiPolygon is a collection of separate filled parts. A centre in any part is selected once.

Outside is still counted.

The chip does not clip the polygon before selection. Centres selected beyond the available raster remain in selected_cell_count and out_of_coverage_cell_count. They contribute unknown support rather than disappearing.

A very small polygon can select no centres. Self-crossing or unclosed rings are rejected. The implementation also bounds vertex counts and candidate-cell counts; it does not claim to accept arbitrary geometry size.

02 / From many cells to a few numbers

Sort the counters into labelled jars.

A histogram counts how many values fall in each category. Think of sorting counters into jars labelled “no loss”, “2021”, “2022” and so on. A reduction turns a collection of cells into a smaller answer: totals, histograms and presence flags.

The live bars below use the same synthetic selection as the grid above. Valid land goes into the year jars. Known water and unknown cells stay separate; they are not land with zero loss.

Selected land / loss-year histogram

Precisely, v1 uses numpy.bincount() from NumPy, Python’s number-array library, on valid land. The loss-year histogram has 26 bins: 0 for no mapped loss and 1–25 for 2001–2025. Its canopy histogram has 101 bins, one for each percentage from 0 to 100. The decision layer uses a 20-bin code histogram instead. Each code already combines the retained land, forest and later-loss facts.

A histogram gives counts, not the geographical pattern of the selected cells. These query outputs need the counts, so the order of the selected codes does not affect them. That property helps make the exhaustive fidelity proof possible.

03 / An answer needs its support

Yes, no and unknown are different.

A tri-state flag has three answers: yes, no or unknown. Think of searching a room with some lights off. Finding an object establishes “yes”. Finding nothing establishes “no” only if the places that could hide it were checked.

Support describes how much usable information backs the calculation. Complete means no required selected-cell information is missing; partial means some is missing; none means there are no selected cells or no usable land cells to analyse. Known water is handled separately and is not missing land.

Try a simple presence question.

This example has ten selected land-or-unknown positions. Unknown positions may hide an event. It illustrates the v1 loss-presence rule, not every JRC-specific condition.

The decision layer adds a question-specific detail. Unknown forest state blocks a confident “no forest”. For “loss on 2020 forest”, unknown forest state only blocks “no” where there is a post-2020 loss that might have occurred on forest. Support is still partial if any selected land lacks the JRC class. A flag and its support describe different things.

v1 also has an unavailable support state when an entire required band is explicitly missing. It forces all selected positions unknown. The decision-layer output itself uses none / partial / complete.

04 / The first build

Two doors into the same query.

The original v1 pipeline is a sequence of processing steps. Think of two delivery vans bringing the same ingredients to the same kitchen: one brings GeoTIFF files; the other brings our compact lossless store. After unpacking, the cooking is identical.

Door A / Original files

GeoTIFF → Rasterio / GDAL

Rasterio is the Python reader; GDAL is the map-file library it calls. Verify source hashes (content fingerprints), sizes and grid labels. Decode three single-band Hansen chips and their validity masks into NumPy arrays.

engine/source.py → load_source()
Door B / Lossless compact store

Index + payload → zstd decoder

Read the compact store’s index and compressed chunks. Restore exactly the same band values, validity masks and grid metadata.

engine/codecs.py → decode_store()
SAME ARRAY SHAPE3 × H × W

Canopy, loss year and datamask, with three boolean masks.

SAME SELECTIONPolygon → centres

Shapely covers on the original native lattice.

SAME REDUCTIONCount the bands

101 canopy bins, 26 loss bins, masks and support.

SAME OUTPUTSCompare every field

Annual counts, period flags, full histograms and unknown reasons.

The retained compact format separates the bands, compresses chunks with Zstandard level 19, and keeps an index. Zstandard is a lossless compression recipe; “level 19” chooses a stronger, more expensive packing setting. The measured candidate uses 1,024-cell chunk edges, so edge chunks can be smaller.

At this stage JRC was a separate verified companion, not part of the retained Hansen v1 query. The later EUDR decision pipeline combines JRC’s baseline with Hansen’s loss at a documented shared sampling location.

05 / Follow the work

Most hot time was choosing cells.

In the plan-time measurement, the 17-plot v1 batch took about 1.6 ms. Polygon selection took about 1.09 ms; roughly 0.51 ms remained for reduction and other query work. A millisecond is one thousandth of a second. These small batches make repeated benchmark measurements necessary.

Choosing a cell requires geometry work: creating candidate centres and asking whether the polygon covers them. The old compressed bytes have already been decoded. Changing their disk format cannot remove that geometry work.

06 / Why compression was not enough

An easier unpack does not change the cooking.

The hot path is the repeated work once data is loaded. Think of a kitchen with all ingredients already on the bench. In v1 both representations become the same arrays, and both call the same selection and reduction functions. Smaller boxes do not make that part faster.

Loading / representation matters

Read → decompress → arrays

Compression can change file-read and decode time, plus the stored size. That affects fresh-process loading. It can help or hurt, depending on the codec.

v1 retained load + query:
11.18 → 5.80 ms

Excludes Python start-up and imports. OS file cache uncontrolled.

Hot / v1 did the same work

Select → reduce → answer

The retained experiment measured 1.418 ms original and 1.446 ms compact. It found no hot speedup.

The later benchmark’s original-v1 median is 1.451 ms. It is a separate run and harness, not evidence that old compression became faster.

Why not squeeze every pixel harder?

Entropy describes uncertainty in the values: a perfectly repeated sheet is easier to describe than a sheet of varied numbers. Think of “write zero a thousand times” versus a long, irregular list. The exact canopy percentages in treecover2000 are expensive to retain and dominate the Hansen bytes.

The project was near a practical compression floor for the lossless choices tested: tuned standard GeoTIFF was already within 0.5% of the custom store, and even slightly smaller. The supplied reports do not establish a mathematical entropy lower bound. “Near the entropy floor” is an intuition here, not a measured theorem about all possible codecs.

The later speedups change the work: a smaller retained representation, exact fast selection, a precomputed cell index for registered plots, and a table of stored answers. These are distinct levers. Follow each lever and its benchmark.

The representation drops unused values; the registered-plot index avoids repeated geometry; the answer table avoids repeated reduction too. For a changed or new boundary, Plotline still has to select cells. It uses the exact fast selector rather than reusing an old answer.
